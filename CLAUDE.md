# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
# Build the whole solution
dotnet build wledBridge.slnx

# Run the web app (applies pending EF Core migrations automatically on startup)
dotnet run --project src/wledBridge.Web

# Run the Virtual Mixer module's unit tests (the only test project so far)
dotnet test tests/wledBridge.VirtualMixer.Tests

# Add a new EF Core migration (must pass both --project and --startup-project)
dotnet ef migrations add <Name> \
  --project src/wledBridge.Infrastructure/wledBridge.Infrastructure.csproj \
  --startup-project src/wledBridge.Web/wledBridge.Web.csproj \
  --output-dir Persistence/Migrations
```

The only test project so far is `tests/wledBridge.VirtualMixer.Tests` (xUnit, covers the Virtual Mixer module's logic: serialization/migration round-trips, the single-active-mixer rule, the thread-safe runtime engine, bindings, curves). The other three original projects have no tests yet. `NuGet.config` at the repo root pins package restore to `nuget.org` only (`<clear/>` + one source) - the machine's globally configured company feed 401s on this network and would otherwise break `dotnet restore`/`dotnet add package` for anyone else on the same machine/account.

The dev server for the `run` skill / preview tooling is `wledBridge.Web` (see `.claude/launch.json`), serving on `http://localhost:5073`. See all devices/templates and export/import JSON at `/devices/overview`, learn/onboard a new controller at `/devices` (also used to edit a saved one via `/devices?editDeviceId=<guid>`), seed one from a built-in driver's layout at `/devices/from-template`, test a saved one at `/devices/test`. Virtual Mixer: manage/import at `/mixer`, design at `/mixer/designer/<guid>`, test at `/mixer/test/<guid>`, view the active mixer scaled at `/mixer/live`, manage color presets at `/mixer/colors`.

## Architecture

Clean Architecture, four projects under `src/`, dependency direction `Web → Infrastructure → Application → Domain`, plus a **standalone, self-contained** `wledBridge.VirtualMixer` module (Razor Class Library) that the Web project references but which depends on nothing in the host - see "Virtual Mixer module" below. Root namespace is `wledBridge` (lowercase, intentional - not a typo).

- **wledBridge.Domain** - no dependencies. Entities: `WledDevice`/`WledState`, and the controller-mapping model `ControllerDevice` (has `ControlDefinitions: List<ControllerControlDefinition>`), `ControllerControlDefinition` (one learned physical control: type/channel/command-code/data-number/LED capability/relative flag), `LedCapability` enum (None/Single/Bar/Rgb), `VirtualMixer`/`VirtualControl`, `ControlMapping`, `ControlType` enum (Pad/Encoder/Fader/Button).
- **wledBridge.Application** - abstractions + orchestration only, no concrete implementations.
  - `Abstractions/Midi`: `IMidiPortFactory`, `IMidiInputPort`, `IMidiOutputPort`, `MidiMessage` (raw status/data1/data2) - bidirectional MIDI transport, swappable (currently NAudio-backed).
  - `Abstractions/Controllers`: `IControllerDriver` (incl. `ExportControlDefinitions()` - every driver, fixed or generic, can describe its full control set as raw `GenericControlDefinition`s; this is what powers "Aus Vorlage erstellen"), `IControllerDriverFactory` (`Create(driverKey)` for fixed drivers, `CreateGeneric(displayName, controls)` for learned ones), `ControlDescriptor`, `ControlValueChangedEventArgs`, `ControllerColor`, `EncoderRingStyle`, `GenericControlDefinition` (record: one learned control's raw address + classification, passed to `CreateGeneric`), `GenericDriverConstants.DriverKey` ("Generic") - the per-controller-model driver contract. New *fixed* controller hardware = new `IControllerDriver` implementation registered in the factory; nothing else changes. New *unknown* hardware needs no code at all - see "Generic/learned controller system" below.
  - `Controllers/ControllerSession` + `ControllerSessionManager`: opens MIDI ports via the port factory, creates a driver via the driver factory (`Connect` for fixed drivers, `ConnectGeneric` for learned ones - both funnel through a shared private `ConnectWithDriver`), wires `IMidiInputPort.MessageReceived/SysExReceived` into `driver.HandleMessage/HandleSysEx`. This is the runtime "glue" - one active session at a time (singleton), used by the Device Test page.
  - `Abstractions/Persistence/IApplicationDbContext`: exposes `DbSet<T>` per aggregate (incl. `ControllerControlDefinitions`); implemented by the EF Core context in Infrastructure.
- **wledBridge.Infrastructure** - concrete adapters.
  - `Midi/NAudio*`: `IMidiPortFactory`/`IMidiInputPort`/`IMidiOutputPort` over NAudio (Windows winmm, so Windows-only).
  - `Controllers/Apc40Mk2Driver` + `Apc40ColorPalette` + `ControllerDriverFactory`: see "APC40 mkII driver" below. New fixed drivers get added to `ControllerDriverFactory`'s dictionary.
  - `Controllers/GenericMidiControllerDriver`: see "Generic/learned controller system" below.
  - `Wled/WledHttpClient`: talks to WLED's `/json/state` HTTP API.
  - `Persistence/`: `WledBridgeDbContext` (Code First, one `IEntityTypeConfiguration<T>` per aggregate in `Persistence/Configurations`), SQLite. Migrations applied automatically at startup in `Program.cs` (`dbContext.Database.Migrate()`), not via CLI on deploy.
- **wledBridge.Web** - Blazor Server + MudBlazor, composition root (`Program.cs` wires `AddApplication()`/`AddInfrastructure()`).
  - Interactivity is **global**, declared once as `<Routes @rendermode="InteractiveServer" />` in `App.razor`. Do **not** add a per-page `@rendermode` - a page-level render mode creates a separate render tree from `MainLayout`, and `MudPopoverProvider` (declared once in `MainLayout.razor`) then isn't reachable from that page, silently breaking every popover-based component (`MudSelect`, `MudColorPicker`, etc.) with no visible error beyond a console log.
  - `Theme/DarkTheme.cs`: dark MudBlazor theme, condensed font (Oswald), Beatport-inspired accent color `#01FF95` (sourced via web search, not scraped from the live site - treat as approximate if it ever needs revisiting).
  - `Components/Pages/DevicesOverview.razor` (`/devices/overview`) lists every saved `ControllerDevice` *and* a synthetic row per fixed driver (`DriverFactory.AvailableDriverKeys`, tagged with a "Vorlage" `MudChip` since it's code, not a DB row). "Export" downloads a `ControllerConfigurationExport` (`Web/Devices/ControllerConfigurationExport.cs`) as JSON via a small JS interop helper (`wwwroot/js/downloadFile.js`'s `downloadFileFromText`, referenced in `App.razor` - Blazor Server has no built-in dynamic-file-download component, and this avoids adding a whole HTTP endpoint just for that). Export works for both actual Generic devices (definitions come from the DB) and any fixed-driver row, template or saved (definitions come from `driver.ExportControlDefinitions()` instead, since those have nothing per-device stored). "Import" uses a plain `<InputFile>` reading the uploaded JSON directly in C# (no endpoint needed there either) and always creates a new **Generic** device regardless of the export's original `DriverKey` - and deliberately drops the imported MIDI port names (they're almost certainly wrong on a different machine) rather than silently carrying over misleading values.
  - `Components/Pages/Device.razor` (`/devices`) is the "Anlernen" (learn) workflow, and also doubles as the editor for an existing generic device via the `editDeviceId` query param (`?editDeviceId=<guid>`, read with `[SupplyParameterFromQuery]`; re-checked in `OnParametersSetAsync` rather than `OnInitializedAsync` since Blazor Server can reuse the component instance across same-route query-string-only navigations). New-device mode: connect to *any* MIDI controller (in+output opened directly via `IMidiPortFactory`, not through `ControllerSessionManager`, since there's no driver yet), click "Anlernen", touch the physical control, the first matching Note/CC message is captured as a candidate address, then the user classifies it (name, `ControlType`, `LedCapability`, relative-encoder switch) and it's added to a running list - the list is a mutable class (`LearnedControlItem`), not a record, so the table cells (name/type/LED/relative) are directly two-way-bound and editable in place for add/remove/edit-in-one-place. "Speichern"/"Aktualisieren" persists (insert or, in edit mode, rename + delete-and-reinsert `ControllerControlDefinition`s for) a `ControllerDevice` with `DriverKey = GenericDriverConstants.DriverKey`.
  - `Components/Pages/DeviceFromTemplate.razor` (`/devices/from-template`) seeds a new editable generic device from a fixed driver's built-in layout via `driver.ExportControlDefinitions()` - lets a known driver (e.g. APC40) become a starting point for customization without re-learning every control by hand. Resulting device links straight to "hier bearbeiten" (`/devices?editDeviceId=`) or Device Test.
  - `Components/Pages/DeviceTest.razor` (`/devices/test`) is the hardware-facing test tool for a *saved* device (fixed driver like APC40 or a saved generic one): connect (branches to `SessionManager.Connect` or `.ConnectGeneric` based on `DriverKey`), live raw MIDI monitor, live parsed control-event log, pad/scene color tester with a themed palette (pads with `Row`/`Column` set on their `ControlDescriptor` render into a real CSS grid matching the physical layout; ones without - e.g. Scene Launch, or *any* control on a Generic-driver device, since `GenericControlDefinition` doesn't carry Row/Column - fall back to a spaced flex-wrap row below), encoder LED-ring tester (Single/Fill/Pan style; `OnControlChanged` also mirrors hardware-driven encoder turns onto the on-screen slider, without pushing the value back out since the device's own ring already tracks its position), button LED tester, physical-to-virtual-mixer mapping table, and a device reset button. The saved-devices list supports inline rename, delete (with an `IDialogService.ShowMessageBoxAsync` confirm), and - for Generic-driver devices only - "Bearbeiten" (navigates to `/devices?editDeviceId=`). Also has a top-right app-bar menu for restarting/exiting the whole process (`Environment.Exit(0)` - see gotcha below).
  - EF Core `IApplicationDbContext` is registered `Scoped`; only ever touched from Blazor-invoked handlers (button clicks, dropdown changes), never from the raw MIDI callback thread, to avoid concurrent access to the same `DbContext` instance.

### APC40 mkII driver

`Apc40Mk2Driver` is built from Akai's official **"APC40 Mk2 Communications Protocol v1.2"** PDF (`docs/APC40Mk2_Communications_Protocol_v1.2.pdf`), verified live against real hardware over the course of this project - trust the code/PDF over intuition here, several plausible-looking guesses turned out wrong:

- Device is put into **Ableton Live Mode** (SysEx mode byte `0x41`) on attach. **Do not** try Alternate Ableton Live Mode (`0x42`) - it was tested and breaks LED ring feedback entirely (device stops auto-rendering ring position), it's not just "an alternate style".
- Pads (and Scene Launch, which uses the identical mechanism): fixed **channel 0**, `note = row*8 + col` (row 0 = bottom, row 4 = top). Color is velocity-encoded via the exact 128-entry palette in `Apc40ColorPalette.cs`, channel 0 = "Primary Color" per the protocol's RGB LED type table.
- Track-scoped controls (faders, activator/solo/record-arm/select/clip-stop/crossfader-assign): **channel = column** (0-7), fixed note/CC per function.
- Device Encoders and Pan/Track Encoders: **absolute** position (per protocol's "Type CC1"), even though they're endless-turning encoders - the firmware tracks and saturates the position internally. Only **Cue Level** and **Tempo Knob** are relative (protocol's "Type CC2": data2 `1-63` = +N, `64-127` = -(128-data2)).
- Encoder **LED ring style** (Single/Volume-fill/Pan) is a **separate CC per encoder** (`0x18-0x1F` device, `0x38-0x3F` track knobs; value `1`/`2`/`3`), sent independently of the position value - the device renders its own tracked position once a style is set, so never push a synthetic value just to "activate" a style (this caused a real bug: forcing 50%/0% values on every connect/style-change, and Volume-style at value 0 renders as fully blank while Single-style at 0 shows one LED, making connect and reset look inconsistent until this was fixed).
- `Reset()` intentionally leaves rings on **Single Position at value 0** (one LED lit), not ring-type-off - a fully-off ring type requires reselecting a style before anything shows again, which was reported as a bug.
- Several buttons (Play/Record/Session Record/Pan/Sends/User/etc.) get their LED lit only if the **host** explicitly sends it - the device does not self-illuminate button LEDs in Ableton Live Mode. `DeviceTest.razor`'s `OnControlChanged` echoes button presses back as `SetButtonLed` calls for this reason.

### Generic/learned controller system

For any controller that isn't (yet) a dedicated `IControllerDriver`, `GenericMidiControllerDriver` is built at runtime from a list of `GenericControlDefinition`s captured via the `/devices` learn UI - no code changes needed for new hardware. Verified end-to-end against the real APC40 mkII (used as a stand-in "unknown" device): connect → Anlernen → press a pad → captured `ch00 status=0x90 data1=26` → classified as Pad/RGB → saved → reloaded on `/devices/test` via `ConnectGeneric` → pad color test round-tripped correctly.

- Input decoding mirrors `Apc40Mk2Driver`'s address-based approach (channel/command-code/data-number lookup) but generically: Note On/Off → Pad/Button (on/off), CC → Encoder/Fader (absolute `data2/127`, or relative accumulate-and-clamp if the control was flagged relative during learning).
- Output/LED feedback is necessarily **best-effort** - an unknown controller's actual feedback protocol can't be inferred just from watching its input. `SetPadColor`/`SetButtonLed` send NoteOn velocity 127 (on) / 0 (off) on the same address as the input; `SetLedRingValue` sends a raw CC with the scaled value. **This does not reproduce true RGB colors** - e.g. on the APC40, sending velocity 127 for "any non-black color" lands on whatever the device's own palette assigns to velocity 127 (confirmed: hex `4B1502`, a dark orange, per `Apc40ColorPalette.cs`), not the color actually picked in the UI. `SetEncoderRingStyle` is a no-op (no generic mechanism known). This is intentional and documented in the driver's XML remarks - don't try to "fix" the color mismatch, it's a fundamental limitation of not knowing the device-specific encoding.
- The dedicated `Apc40Mk2Driver`/`ControllerDriverFactory.Create("Apc40Mk2")` path is kept fully intact as the "device template" for known hardware - the generic system is an addition, not a replacement. `DeviceTest.razor`'s "Als Gerät speichern" button is disabled when the connected driver is already `GenericDriverConstants.DriverKey`, since that device was already persisted with its control definitions during the learn flow (re-saving would create a duplicate without them).
- Known limitation: `GenericControlDefinition`/`ControllerControlDefinition` don't carry `Row`/`Column`, so a device saved as Generic (whether hand-learned or seeded via "Aus Vorlage erstellen" from APC40) always renders its pads in the flex-wrap fallback on Device Test, never the positioned grid - even though the APC40 template it came from had grid positions. Fixing this would mean threading Row/Column through the generic model and a migration; not done since no one has asked for it yet.

### Virtual Mixer module (`src/wledBridge.VirtualMixer`, standalone RCL, tests in `tests/wledBridge.VirtualMixer.Tests`)

A deliberately self-contained, reusable module for building touch/mouse mixer surfaces. **It references nothing in the host** - the dependency arrows only point Host → VirtualMixer. Integration is `builder.Services.AddSignalR(); builder.Services.AddVirtualMixer(o => o.StoragePath = ...)` in `Program.cs`, plus `app.MapVirtualMixerApi()` for the opt-in remote API; the host provides thin pages (`Components/Pages/Mixer*.razor`, routes `/mixer`, `/mixer/live`, `/mixer/colors`, `/mixer/designer/{id}`, `/mixer/test/{id}`) that just embed the module's public components and own the routing/nav.

- **Public surface** (only these; everything else is `internal`): DI `AddVirtualMixer`/`VirtualMixerOptions`; services `IVirtualMixerManager` (CRUD + the single-active-mixer rule, enforced *inside* the module, + JSON export/import) and `IVirtualMixerRuntime` (thread-safe external control: `SetControlValueAsync`/`SetButtonStateAsync`/`SetLedAsync`/`SetSubValueAsync`/`SendCommandAsync` + `ControlEvent`); components `<VirtualMixer/>` (runtime view of the active or an explicit mixer, 5 sizing modes incl. `FitToContainer`), `<VirtualMixerDesigner/>`, `<VirtualMixerManager/>`, `<VirtualMixerTestView/>`, `<ColorPresetManager/>`; `IControlDescriptor` (host can add custom control types via `options.AddControlType<T>()`); `IVirtualMixerStore` (host can replace the default JSON-file store via `options.UseStore<T>()`).
- **State engine** (`State/MixerRuntimeState`, singleton): the *single* mutation path is a `Channel<IControlCommand>` consumed by one background task - UI interaction, external API, bindings and network all enqueue the same typed commands, which is what makes it thread-safe from MIDI-callback threads. High-frequency `SetValue`/`SetSubValue` are coalesced per control per drained batch. Changes fan out as (a) per-control notifications for render isolation (`ControlRendererBase` subscribes only to its own control's changes - a fader sweep never re-renders the whole surface) and (b) typed public events (`ControlEventArgs` hierarchy: Pressed/Released/ValueChanged/StateChanged/DeltaChanged/Rejected). Runtime state is strictly separated from the persisted definition and is **transient** (Q-011: no last-value restore).
- **Model** (`Models/`): `MixerDefinition` → ordered `MixerGroup` lanes (full mixer height, grow horizontally, collapsible with the following lanes shifting left - Q-005 lane model) → `ControlInstance` (common props only; **integer logical pixels**, Q-002; type-specific data in polymorphic `ControlSettingsBase`). `ControlBinding` (source→transform→target, evaluated in the state consumer with a depth limit for cycle protection - Q-006/S-006 generic binding engine, the statusbar's data source is just the first use). `Curve` (Linear/Exponential/Logarithmic + one γ param, Q-008). Built-in control types: `button` (Momentary/Toggle/Trigger + Amber/RGB LED), `fader`, `statusbar`, `knob` (Absolute value vs. Relative delta-events, Q-009 single type with a mode), `knobbank` (n mini-knobs, configurable layout).
- **Serialization** (`Persistence/Serialization/MixerJsonSerializer`): System.Text.Json with a registry-backed polymorphic converter (the discriminator is the control's `TypeKey`, resolved through `ControlRegistry`, so host-registered custom types serialize with zero module changes) + `SchemaVersion` and an `IDefinitionMigration` chain run on the raw `JsonNode` before deserialization (S-008). Default persistence is one JSON file per mixer under `VirtualMixerOptions.StoragePath` (Q-001; the host points this at `virtualmixer-data/`, which is git-ignored).
- **Designer** (`Designer/DesignerState` + `Components/VirtualMixerDesigner.razor`): works on a deep-cloned working copy; **every** mutation is an undoable `IDesignerCommand` (S-001), which is what makes undo/redo, multi-select move/delete, align/distribute, copy-paste (JSON clipboard, cross-mixer), duplicate and control templates all fall out without special cases. Selection is a `HashSet<Guid>` (multi-select from the start). Overlap is allowed but flagged (Q-003). Snaplines are magnetic (±4px, S-005). Keyboard nudging (arrows = 1px, Shift = 10px), Ctrl+Z/Y/C/V/D. Config sidebar shows common props + the type's `SettingsEditorComponent` (from the registry) + a bindings editor; edits route through mergeable commands (rapid edits = one undo step).
- **Rendering is shared**: `Components/Internal/MixerSurface` renders a definition identically for designer and runtime - the designer just overlays an adorner layer (selection, resize handles, wrench). There is exactly one rendering path, so designer and runtime can never drift. Drag/resize/fader/knob interaction is driven by a small pointer-events JS module (`wwwroot/virtualmixer.js`) that keeps the high-frequency movement client-side (CSS transform / `--vm-pos` custom property) and only commits to the server on drop - essential on Blazor Server where every event is a SignalR round trip. `FitToContainer` computes an initial scale from the container rect on attach and then tracks a `ResizeObserver` (scaling is a pure render-time CSS transform - it never mutates stored positions/sizes, per requirement 4).
- **Remote control** (`Http/`, opt-in via `MapVirtualMixerApi(prefix = "/api/virtualmixer")`, Q-016 REST + SignalR): REST command/query endpoints plus a bidirectional `VirtualMixerHub`; a `VirtualMixerEventBridge` (`IHostedService`) broadcasts runtime events to hub clients but stays **dormant unless the host registered SignalR** (`IHubContext` resolves to null → never subscribes), so the core stays SignalR-agnostic. Securing these endpoints is the host's responsibility. Verified end-to-end: `POST /api/virtualmixer/controls/{id}/value` → command channel → state → the fader's `--vm-pos` in the live view moved to match.
- The colors module (`IColorPresetService`) is module-owned (Q-007: persisted presets + a transient "recently used" row, max 8). Contrast/text colors use WCAG relative luminance (`Components/Internal/ColorUtils`); group/control background colors render via an alpha overlay so the stored hex stays untouched.
- **Note on name collision**: the host's *old* `wledBridge.Domain.Controllers.VirtualMixer`/`VirtualControl`/`ControlMapping` entities and the Device Test "Virtuelles Mischpult – Zuweisung" table are a **separate, pre-existing** feature, intentionally left untouched (Q-015). They are unrelated to this module; don't confuse `wledBridge.VirtualMixer.*` (the module) with `wledBridge.Domain.Controllers.VirtualMixer` (the old entity).

### Known gotchas already solved (don't reintroduce)

- **Shutdown**: use `Environment.Exit(0)`, not `IHostApplicationLifetime.StopApplication()` - the latter waits for open connections (including the SignalR circuit the shutdown request came in on) to drain and can hang indefinitely.
- **MudPopoverProvider**: see the Web bullet above - one global render mode, not per-page.
- **File locks during `dotnet build`**: a previously-started `dotnet run`/preview process holds the output DLLs/EXE open; stop it first (or check `dotnet ef`/build errors mentioning `wledBridge.Web.exe`/`.dll` locked by another process).
- **Virtual Mixer module independence**: never add a reference from `wledBridge.VirtualMixer` to any host project - the whole point is Host → VirtualMixer only. Host-specific needs are abstracted behind the module's public interfaces/events (e.g. a future MIDI→mixer bridge subscribes to `IVirtualMixerRuntime.ControlEvent` and pushes via its command methods, from the host side).

## Status

Implemented: Clean Architecture skeleton, bidirectional MIDI transport, controller driver framework with a verified APC40 mkII driver, a generic/learned-controller system (`/devices` learn UI + `GenericMidiControllerDriver`, verified end-to-end against real hardware) for any other MIDI controller, seeding a new device from a fixed driver's template (`/devices/from-template`), full CRUD on saved devices (rename/delete on Device Test, edit controls via `/devices?editDeviceId=`), a devices overview with JSON export/import (`/devices/overview`), EF Core/SQLite persistence, Device Test page (generalized to work with both fixed and learned drivers, with a proper positioned pad grid where layout data is available), and a **standalone Virtual Mixer module** (`wledBridge.VirtualMixer` RCL: mixer designer with drag/resize/undo-redo/groups/bindings/templates, runtime component with 5 sizing modes, event monitor, color presets, simulation mode, opt-in REST+SignalR remote control; 30 unit tests; verified end-to-end in the browser - see "Virtual Mixer module" above).

Not yet built: WLED device management UI (entity + HTTP client exist, no CRUD UI); the actual MIDI-control → WLED-action mapping/routing engine; and a bridge wiring the existing MIDI `ControllerSession` events into the Virtual Mixer module's `IVirtualMixerRuntime` (the module exposes the seam - `ControlEvent` + the command methods - but no host-side glue connects hardware to a mixer yet). The old `Domain.Controllers.VirtualMixer` entity + Device Test mapping table remain as a separate legacy feature, untouched.
